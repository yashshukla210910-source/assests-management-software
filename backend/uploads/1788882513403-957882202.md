## 1. Product Overview

**DecentraVault** is an enterprise-grade, decentralized identity and asset management platform built for organizations that need:

- Tamper-proof, cryptographically verified digital identities
- Blockchain-anchored ownership of digital and physical assets
- Role-based access control enforced at backend and smart-contract layers
- Immutable, auditable history of every identity, asset, and permission change

The platform replaces fragile, centralized IAM + asset-tracking systems with a hybrid on-chain/off-chain architecture. Blockchain provides the *trust layer*; a conventional backend and relational database provide the *usability layer*. The UI deliberately looks and feels like enterprise SaaS (think ServiceNow, AssetPanda, Okta) — not a crypto wallet.

| **Auth** | JWT (short-lived) + refresh tokens; wallet signature for DID proof | Separates app session from cryptographic identity |

| **File/Doc Storage** | Local filesystem (dev) / MinIO S3-compatible (prod) | Off-chain metadata storage |
| **Audit integrity** | Merkle-hash chaining of audit records | Tamper-evident without putting every log on-chain |

### Data Flow Principle
- **Primary source of truth for ownership**: blockchain (NFT owner mapping)
- **Primary source of truth for identity metadata, roles, permissions**: PostgreSQL (synced from blockchain events)
- **Audit events**: originated off-chain, hashed and anchored on-chain via `AuditRegistry`
- **Frontend never calls blockchain directly** in normal flows — the backend mediates, preventing key exposure

## 8. Main User Flows

### Flow 1 — Admin Creates Identity
```
Admin clicks "New Identity"
  → Form: name, email, org, initial role
  → Backend: generates Ethereum key-pair in secure server context
  → Backend: creates DID document (did:ethr:<address>)
  → Smart Contract: IdentityRegistry.registerIdentity(did, address, metadataHash)
  → PostgreSQL: insert User + DID + DID_Document rows
  → Audit: IDENTITY_CREATED event (hashed, anchored to AuditRegistry)
  → UI: identity appears in list with status "Active"
  → (Optional) Credential email sent to new user with one-time key claim link
```

### Flow 2 — Admin Mints Asset
```
Admin clicks "Mint Asset"
  → Form: name, category, description, location, metadata
  → Backend validates inputs + permissions
  → Backend: IPFS-style hash of metadata stored in off-chain storage
  → Smart Contract: AssetRegistry.mintAsset(tokenId, metadataHash, ownerDID)
  → NFT minted to platform custody address or admin's DID address
  → PostgreSQL: insert Asset + AssetMetadata rows; initial Ownership record
  → Audit: ASSET_MINTED event
  → UI: asset appears in table with status "Minted / Unassigned"
```

### Flow 3 — Asset Assignment / Transfer
```
Admin/Manager selects asset → "Assign" or "Transfer"
  → Select target identity (DID)
  → Backend: checks `asset.assign` / `asset.transfer` permission
  → Backend: calls AssetRegistry.transferAsset(tokenId, fromDID, toDID)
  → Blockchain emits Transfer event
  → Backend indexer catches event → updates Ownership record
  → Audit: ASSET_ASSIGNED / ASSET_TRANSFERRED event
  → Notification: target identity notified
  → UI: ownership timeline updated; previous/new owner shown
```

### Flow 4 — Auditor Verifies Asset
```
Auditor opens Verification screen
  → Enters Asset ID or scans QR
  → Backend: reads AssetRegistry.ownerOf(tokenId) from chain
  → Backend: fetches ownership history from OwnershipRecord table (blockchain-synced)
  → Backend: verifies metadataHash matches stored metadata (integrity check)
  → UI: displays
      ✓ VERIFIED
      Asset: [name] | Token ID: [id]
      Current Owner DID: did:ethr:0x...
      Blockchain Record: Block #xxxxx | Tx: 0x...
      Ownership History: [timeline]
      Last Verified: [timestamp]
```

### Flow 5 — Admin Changes Role Permissions
```
Admin opens Roles & Permissions
  → Selects role → clicks permission toggle
  → Confirmation dialog: "Removing asset.transfer from Manager affects N users"
  → Admin confirms
  → Backend: updates RolePermission row
  → Smart Contract: AccessControl.updatePermission(roleId, permission, granted)
  → Audit: PERMISSION_UPDATED event with before/after state
  → All active sessions for affected role have permission cache invalidated
  → UI: permission matrix updates; affected users count shown
```

### Flow 6 — User Views Own Identity & Assets
```
User logs in → Dashboard shows personal summary
  → Clicks "My Identity" → sees own DID, verification status, role badge
  → Clicks "My Assets" → filtered asset list (own only)
  → Clicks any asset → Asset Details: NFT info, current owner (self), history
  → Clicks "Verify" → runs verification → sees green "VERIFIED" result
```

## 9. Database Schema

### Core Tables

```sql
-- Users: application account
CREATE TABLE users (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email           TEXT UNIQUE NOT NULL,
  name            TEXT NOT NULL,
  organization    TEXT,
  status          TEXT NOT NULL DEFAULT 'active', -- active | inactive | revoked
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- DIDs: decentralized identifiers
CREATE TABLE dids (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id),
  did             TEXT UNIQUE NOT NULL, -- did:ethr:0x...
  address         TEXT NOT NULL,        -- Ethereum address (public)
  public_key      TEXT NOT NULL,        -- compressed secp256k1 pub key (hex)
  status          TEXT NOT NULL DEFAULT 'active', -- active | revoked | suspended
  method          TEXT NOT NULL DEFAULT 'ethr',
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at      TIMESTAMPTZ
);

-- DID Documents: W3C DID Document snapshot (off-chain cache)
CREATE TABLE did_documents (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  did_id          UUID NOT NULL REFERENCES dids(id),
  document        JSONB NOT NULL,
  version         INT NOT NULL DEFAULT 1,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Roles
CREATE TABLE roles (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name            TEXT UNIQUE NOT NULL, -- admin | manager | auditor | user
  display_name    TEXT NOT NULL,
  description     TEXT,
  is_system       BOOLEAN NOT NULL DEFAULT false, -- system roles cannot be deleted
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Permissions (enumerated)
CREATE TABLE permissions (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  key             TEXT UNIQUE NOT NULL, -- e.g. asset.transfer
  domain          TEXT NOT NULL,        -- identity | asset | role | audit | admin
  description     TEXT NOT NULL
);

-- Role ↔ Permission mapping
CREATE TABLE role_permissions (
  role_id         UUID NOT NULL REFERENCES roles(id),
  permission_id   UUID NOT NULL REFERENCES permissions(id),
  granted         BOOLEAN NOT NULL DEFAULT true,
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_by      UUID REFERENCES users(id),
  PRIMARY KEY (role_id, permission_id)
);

-- User ↔ Role assignment
CREATE TABLE user_roles (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id),
  role_id         UUID NOT NULL REFERENCES roles(id),
  assigned_by     UUID REFERENCES users(id),
  assigned_at     TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  revoked_at      TIMESTAMPTZ
);

-- Assets (off-chain metadata)
CREATE TABLE assets (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  asset_code      TEXT UNIQUE NOT NULL,   -- human-readable: AST-0001
  name            TEXT NOT NULL,
  category        TEXT NOT NULL,
  description     TEXT,
  location        TEXT,
  status          TEXT NOT NULL DEFAULT 'minted', -- minted | assigned | transferred | revoked
  token_id        BIGINT UNIQUE,          -- NFT token ID on-chain (null until minted)
  contract_address TEXT,                 -- which contract holds this NFT
  metadata_hash   TEXT,                  -- keccak256 of metadata JSON
  created_by      UUID NOT NULL REFERENCES users(id),
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Asset metadata (flexible key-value)
CREATE TABLE asset_metadata (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  asset_id        UUID NOT NULL REFERENCES assets(id),
  key             TEXT NOT NULL,
  value           TEXT,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Ownership records (synced from blockchain events)
CREATE TABLE ownership_records (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  asset_id        UUID NOT NULL REFERENCES assets(id),
  owner_did       TEXT NOT NULL,
  owner_user_id   UUID REFERENCES users(id),
  from_did        TEXT,                   -- null on first mint
  tx_hash         TEXT,                   -- blockchain transaction
  block_number    BIGINT,
  transferred_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  is_current      BOOLEAN NOT NULL DEFAULT true
);

-- Auth tokens (refresh token store)
CREATE TABLE auth_tokens (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id),
  token_hash      TEXT NOT NULL,
  expires_at      TIMESTAMPTZ NOT NULL,
  revoked_at      TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Audit events (off-chain tamper-evident log)
CREATE TABLE audit_events (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  sequence_no     BIGSERIAL UNIQUE,       -- monotonic sequence
  event_type      TEXT NOT NULL,          -- IDENTITY_CREATED | ASSET_MINTED | ...
  actor_user_id   UUID REFERENCES users(id),
  actor_did       TEXT,
  entity_type     TEXT,                   -- identity | asset | role | permission
  entity_id       TEXT,
  action          TEXT NOT NULL,
  payload         JSONB,                  -- before/after state diff
  status          TEXT NOT NULL DEFAULT 'success', -- success | failed
  tx_hash         TEXT,                   -- blockchain tx if applicable
  prev_event_hash TEXT,                   -- hash of previous event (chain)
  event_hash      TEXT NOT NULL,          -- keccak256(sequence + data + prev_hash)
  anchored_tx_hash TEXT,                  -- AuditRegistry anchor tx
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Blockchain transaction cache (avoid re-querying RPC for every detail view)
CREATE TABLE tx_cache (
  tx_hash         TEXT PRIMARY KEY,
  block_number    BIGINT,
  block_timestamp TIMESTAMPTZ,
  from_address    TEXT,
  to_address      TEXT,
  contract_address TEXT,
  function_name   TEXT,
  decoded_input   JSONB,
  status          TEXT,                   -- success | failed | pending
  gas_used        BIGINT,
  cached_at       TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Verification records
CREATE TABLE verification_records (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  type            TEXT NOT NULL,          -- identity | asset | ownership
  subject_id      TEXT NOT NULL,          -- DID or asset_id
  verifier_user_id UUID REFERENCES users(id),
  result          TEXT NOT NULL,          -- verified | failed | pending
  details         JSONB,
  blockchain_confirmed BOOLEAN,
  verified_at     TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Notifications
CREATE TABLE notifications (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id),
  type            TEXT NOT NULL,          -- asset_assigned | role_changed | ...
  title           TEXT NOT NULL,
  body            TEXT,
  entity_type     TEXT,
  entity_id       TEXT,
  is_read         BOOLEAN NOT NULL DEFAULT false,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

### Key Design Decisions
- **Private keys are NEVER stored in the database.** Server-side key generation stores only the encrypted private key in a separate secrets store (environment variable / HSM / Vault), indexed by DID.
- `ownership_records.is_current` flag is maintained by a trigger; only one current record per asset.
- `audit_events.event_hash` creates a tamper-evident chain: any modification to a past event breaks the chain from that point forward.
- `tx_cache` allows the UI to show blockchain details without hammering the RPC endpoint.

### Contract Overview

```

│               DecentraVault Smart Contracts           │
│                                                      │

│           │                       │                  │
│  ┌────────▼───────────────────────▼───────────────┐ │

│  │   (OpenZeppelin AccessControl base)             │ │
│  │                                                 │ │
│  │  grantRole() / revokeRole()                     │ │
│  │  hasRole() / checkPermission()                  │ │
│  │  ADMIN_ROLE / MANAGER_ROLE / AUDITOR_ROLE       │ │
│  └─────────────────────────────────────────────────┘ │
│                                                      │
│  ┌─────────────────────────────────────────────────┐ │
│  │              AuditRegistry                      │ │
│  │  anchorEvent(bytes32 eventHash) external        │ │
```

### Contract 1: `DVAccessControl.sol`

```solidity
// Extends OpenZeppelin AccessControl
// Roles: ADMIN_ROLE, MANAGER_ROLE, AUDITOR_ROLE, USER_ROLE
// Functions:
//   grantRole(bytes32 role, address account)   — only ADMIN_ROLE
//   revokeRole(bytes32 role, address account)  — only ADMIN_ROLE
//   hasRole(bytes32 role, address account)     — view
// Events:
//   RoleGranted(role, account, sender)
//   RoleRevoked(role, account, sender)
```

### Contract 2: `IdentityRegistry.sol`

```solidity
// Storage:
//   mapping(string => Identity) identities;   // DID → Identity
//   struct Identity {
//     address owner;          // Ethereum address controlling this DID
//     bytes32 metadataHash;   // keccak256 of off-chain metadata JSON
//     Status status;          // Active | Suspended | Revoked
//     uint256 createdAt;
//     uint256 updatedAt;
//   }
//
// Functions:
//   registerIdentity(string did, address owner, bytes32 metadataHash)
//     — onlyRole(ADMIN_ROLE)
//   updateIdentity(string did, bytes32 newMetadataHash)
//     — onlyRole(ADMIN_ROLE) or DID owner
//   revokeIdentity(string did)
//     — onlyRole(ADMIN_ROLE)
//   getIdentity(string did) → Identity (view)
//   verifyIdentity(string did, bytes signature) → bool
//     — verifies that msg.sender controls the DID's address
//
// Events:
//   IdentityRegistered(string did, address owner, uint256 timestamp)
//   IdentityUpdated(string did, bytes32 metadataHash, uint256 timestamp)
//   IdentityRevoked(string did, uint256 timestamp)
```

### Contract 3: `AssetRegistry.sol`

```solidity
// Extends ERC721 + ERC721URIStorage (OpenZeppelin)
// Also uses DVAccessControl for minting/transfer guards
//
// Storage:
//   mapping(uint256 => AssetRecord) assetRecords;
//   struct AssetRecord {
//     string ownerDID;        // current DID owner
//     bytes32 metadataHash;   // off-chain metadata integrity
//     Status status;          // Active | Revoked
//   }
//   _tokenIdCounter (auto-incrementing)
//
// Functions:
//   mintAsset(address to, string ownerDID, bytes32 metadataHash, string tokenURI)
//     — onlyRole(ADMIN_ROLE)
//     — returns tokenId
//   transferAsset(uint256 tokenId, string fromDID, string toDID, address newOwner)
//     — onlyRole(ADMIN_ROLE) or onlyRole(MANAGER_ROLE) with permission check
//   revokeAsset(uint256 tokenId)
//     — onlyRole(ADMIN_ROLE)
//   verifyAsset(uint256 tokenId) → (ownerDID, metadataHash, status)  view
//
// Events:
//   AssetMinted(uint256 tokenId, string ownerDID, address mintedTo, uint256 timestamp)
//   AssetTransferred(uint256 tokenId, string fromDID, string toDID, uint256 timestamp)
//   AssetRevoked(uint256 tokenId, uint256 timestamp)
//
// Security:
//   Override transferFrom / safeTransferFrom to require ADMIN or MANAGER role
//   This prevents unauthorized ERC-721 transfers outside the platform
```

### Contract 4: `AuditRegistry.sol`

```solidity
// Gas-efficient on-chain audit anchoring
// Does NOT store full event data — only content-addressed hashes
//
// Storage:
//   mapping(bytes32 => AnchorRecord) anchors;
//   struct AnchorRecord {
//     address anchoredBy;
//     uint256 timestamp;
//     bool exists;
//   }
//
// Functions:
//   anchorEvent(bytes32 eventHash) external onlyRole(ADMIN_ROLE or BACKEND_ROLE)
//   verifyAnchor(bytes32 eventHash) external view → (exists, timestamp, anchoredBy)
//
// Events:
//   EventAnchored(bytes32 eventHash, address anchoredBy, uint256 timestamp)
//
// Design:
//   The backend computes eventHash = keccak256(abi.encode(sequenceNo, eventType,
//     actorDID, entityId, actionData, timestamp, prevEventHash))
//   and anchors it. Auditors can recompute the hash from off-chain data
//   and verify it against the contract — proving the log has not been altered.
```

### Upgradeability
- Use **OpenZeppelin Transparent Proxy** (UUPS) for `IdentityRegistry` and `AssetRegistry` — these may evolve.
- `AuditRegistry` is intentionally non-upgradeable for maximum trust.
- `DVAccessControl` is non-upgradeable; role changes are runtime operations.

### Security Considerations
- All state-modifying functions use `onlyRole` guards at contract level.
- `AssetRegistry` overrides ERC-721 transfer functions to enforce platform RBAC — preventing direct wallet transfers that would bypass audit logging.
- No private keys, emails, names, or PII stored on-chain.
- Reentrancy guards on `mintAsset` and `transferAsset`.
- Integer overflow/underflow protected by Solidity 0.8.x default checked arithmetic.

## 11. DID Architecture

### Standard
We use **`did:ethr`** (ERC-1056 compatible), which maps a DID to an Ethereum address.

```
DID format: did:ethr:<chainId>:<address>
Example:    did:ethr:80001:0x4f5e3c...
```

### DID Lifecycle

```
1. KEY GENERATION
   Backend generates secp256k1 key pair (never leaves server in plaintext)
   Address = keccak256(pubkey)[12:]
   DID = "did:ethr:" + chainId + ":" + address

2. DID DOCUMENT CREATION (W3C compatible)
   {
     "@context": ["https://www.w3.org/ns/did/v1"],
     "id": "did:ethr:80001:0x4f5e...",
     "verificationMethod": [{
       "id": "#key-1",
       "type": "EcdsaSecp256k1VerificationKey2019",
       "controller": "did:ethr:80001:0x4f5e...",
       "publicKeyHex": "0x04abc..."
     }],
     "authentication": ["#key-1"]
   }

3. ON-CHAIN REGISTRATION
   IdentityRegistry.registerIdentity(did, address, metadataHash)

4. AUTHENTICATION (DID Proof)
   Challenge: server sends nonce to client
   Response:  client signs nonce with DID private key → signature
   Verify:    ecrecover(nonce, signature) == DID address → identity confirmed

5. KEY ROTATION (if needed)
   Generate new key pair
   IdentityRegistry.updateIdentity(did, newAddress, newMetadataHash)
   Old key marked revoked in DID document

6. REVOCATION
   IdentityRegistry.revokeIdentity(did)
   Status set to REVOKED on-chain and in database
```

### Private Key Management Strategy
- **Dev/Demo**: Keys generated server-side, stored AES-256 encrypted in `server.env` keyed by DID (acceptable for hackathon scope)
- **Production recommendation**: Hardware Security Module (HSM) or a secrets manager (HashiCorp Vault), keys never in database
- **Frontend**: Never receives or stores private keys; DID proofs use server-side signing for assigned identities; own-account operations use a session challenge flow

### Relationship: DID ↔ Application Account
```
User (application account, email/password)
  └── has one DID (1:1)
       └── DID controls an Ethereum address
            └── address is registered in IdentityRegistry contract
                 └── address owns NFTs in AssetRegistry contract
```

## 13. Security Architecture

### Threat Model & Mitigations

| Threat | Mitigation |
|--------|-----------|
| **Private key theft** | Keys never in DB; server-side only; AES-256 encrypted in secrets store |
| **Unauthorized identity creation** | `identity.create` requires `ADMIN_ROLE` at API middleware AND smart contract |
| **Unauthorized asset transfer** | Permission check at API layer + smart contract `onlyRole` guard |
| **NFT transfer bypass** | `transferFrom` overridden in `AssetRegistry` to require platform role |
| **JWT token theft** | Short-lived JWTs (15 min); refresh tokens are single-use and stored as hashes |
| **Replay attacks** | Nonce-based DID challenge; blockchain tx nonces prevent replay on-chain |
| **Audit log tampering** | Hash-chained audit events; root hashes anchored on `AuditRegistry` contract |
| **SQL injection** | Prisma parameterized queries; never raw SQL from user input |
| **XSS** | React escapes by default; Content-Security-Policy header |
| **CSRF** | JWT in Authorization header (not cookie); CORS restricted to known origins |
| **Unauthorized API access** | JWT middleware on all routes; RBAC middleware checks permission per route |
| **Duplicate transactions** | Idempotency keys on minting/transfer endpoints; DB unique constraints |
| **Stale ownership data** | Ownership always re-verified from chain on verification requests |
| **Frontend permission bypass** | Frontend hides UI elements but backend enforces all permissions independently |
| **Rate limiting** | express-rate-limit on auth endpoints; general rate limiting on all routes |
| **Dependency vulnerabilities** | npm audit in CI; Dependabot alerts |
| **Secrets in code** | All secrets via environment variables; `.env` in `.gitignore` |

### Authorization Enforcement Layers

```
1. FRONTEND   — hides/shows UI elements based on user role (UX only; not security)
2. API MIDDLEWARE — validates JWT, extracts user, checks RBAC permission for route
3. BACKEND SERVICE — additional business rule validation (ownership, scope limits)
4. SMART CONTRACT — final enforcement for all on-chain state changes
```

Never rely on layer 1 or 2 alone. All sensitive operations are guarded at layers 3 AND 4.

## 14. Audit Architecture

### Audit Event Types
```
IDENTITY_CREATED        ROLE_ASSIGNED          ASSET_MINTED
IDENTITY_UPDATED        ROLE_REVOKED           ASSET_ASSIGNED
IDENTITY_VERIFIED       PERMISSION_GRANTED     ASSET_TRANSFERRED
IDENTITY_REVOKED        PERMISSION_REVOKED     ASSET_REVOKED
USER_LOGIN              ACCESS_DENIED          VERIFICATION_RUN
USER_LOGOUT             CONFIG_CHANGED         SYSTEM_EVENT
```

### Tamper-Evidence Mechanism
```
Event N:
  sequence_no  = N
  data         = {type, actor, entity, action, payload, timestamp}
  prev_hash    = event_hash of event N-1 (null for N=1)
  event_hash   = keccak256(sequence_no || data || prev_hash)

Every 100 events (configurable), the backend anchors:
  AuditRegistry.anchorEvent(event_hash of event 100, 200, 300, ...)

To verify integrity:
  1. Fetch all events from PostgreSQL
  2. Recompute hash chain from event 1
  3. For any anchored event, call AuditRegistry.verifyAnchor(hash)
  4. If all match → log is provably unmodified
```

### Audit UI Features
- Filterable by: actor, entity, event type, date range, tx hash, role
- Color-coded by event severity: info / warning / critical
- Expandable rows showing payload diff (before → after)
- "View on chain" link for anchored events
- Export to CSV/JSON for compliance

## 20. Risks & Weaknesses

| Risk | Severity | Mitigation |
|------|----------|-----------|
| **Key management complexity** | High | Simplify to server-side key management for hackathon; document production HSM path |
| **Blockchain latency in UI** | Medium | Show optimistic UI update; background blockchain confirmation with toast |
| **Gas costs for every audit event** | Medium | Batch anchor every N events, not every single event; reduces cost 100x |
| **Smart contract bugs** | High | Use OpenZeppelin primitives; write unit tests in Hardhat |
| **DID standard compliance gaps** | Low | did:ethr is well-established; note deviation from W3C DID-Core where applicable |
| **RBAC drift** (on-chain vs DB out of sync) | Medium | Event-driven sync; re-sync job; on-chain always authoritative for transfers |
| **Demo network instability** | Medium | Use local Hardhat node for SIH demo; do not depend on public testnet |
| **Scope creep** | High | Implement only features directly required by the problem statement |
| **Data volume in audit table** | Low | Pagination; index on timestamp + event_type; export for offline analysis |
| **Session key exposure** | Medium | HTTP-only cookies or Authorization header; never localStorage for JWT |
